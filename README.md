# Задание 1. Анализ и планирование


### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах через веб-интерфейс
- Система поддерживает регистрацию датчиков отопления при включении

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс
- Система поддерживает получение данных о температуре с датчиков, установленных в домах

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования**: Go
- **База данных**: PostgreSQL
- **Архитектура**: Монолитная, все компоненты системы (UI-логика, бизнес-логика, управление устройствами, работа с БД) находятся в одном приложении.
- **Взаимодействие**: Синхронное, через HTTP-запросы с телами в виде JSON-сообщений, запросы обрабатываются последовательно.
- **Масштабируемость**: Ограничена, так как монолит сложно масштабировать по частям.
- **Развертывание**: Любое обновление требует полной остановки системы.
- **Отказоустойчивость**: Низкая. Проблемы с работой приложения на промышленной среде приводят к недоступности всего функционала - как считывания информации с датчиков, так и управления отоплением, а также регистрации устройств.
- **Безопасность**: Низкая. Учет пользователей отсутствует. Любой пользователь может просмотреть информацию и управлять любым устройством, зная его ID и/или местоположение, что делает их уязвимыми для атак.
- **Расширяемость**: API и структура БД теоретически поддерживает добавление новых видов устройств (с помощью полей с типом устройства и единицей изменения).

### 3. Определение доменов и границы контекстов

- **Домен: Управление устройствами**
  - Контекст: Регистрация устройств, привязка к дому/пользователю, конфигурация реле/датчиков.
  - Контекст: Управление жизненным циклом устройства (provisioning, firmware tags, статус "online/offline").
- **Домен: мониторинг**
  - Контекст: Получение данных с датчиков.
- **Домен: Управление климатом**
  - Контекст: включение/выключение отопления.


### **4. Проблемы монолитного решения**

- **Масштабирование:** Невозможность масштабировать отдельные части системы независимо.
- **Высокая связанность:** Любое изменение в бизнес-логике или добавлении нового устройства затрагивает весь кодовый базис и требует полного деплоя.
- **Биллинг/Новые сервисы:** Трудно быстро добавлять новые продукты (управление освещением, безопасностью и т.д.).
- **Оборудование:** Ручная установка → высокая стоимость ввода в эксплуатацию; плохо масштабируется на большом количестве домов.
- **Надёжность и отказоустойчивость:** Один монолит и одна БД — единственные точки отказа; нет очередей/буферизации для временных сетевых разрывов.
- **Развертывание / CI/CD:** Нельзя развернуть часть функционала отдельно, что увеличивает риск и длительность релизов.

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия микросервисов будут иcпользованы как синхронный REST API, так и асинхронное взаимодействие (например, через брокер сообщений).  

*Синхронный* API будет использоваться для:

- получения информации об устройстве. Пользователь ждет немедленного отображения данных; ошибка обращения к устройству должна быть обработана сразу же.
- отправка команды устройству. Когда пользователь выполняет команду, например "включить свет" - он ожидает немедленной обратной связи, либо выполнения операции, либо сообщения об ошибке.
- создания правил автоматизации. Пользователь создает правило через UI (например, если температура ниже 18 градусов - включить отопление) и должен сразу увидеть результат: правило сохранено, устройство не доступно и т.п.

*Асинхронный* API будет использоваться для:

- отправка устройствами событий об изменении своего состояния, например: изменилась температура. Здесь не требуется немедленной реакции пользователя, достаточно просто получить новые данные и обновлить их сервисе управления устройствами.
